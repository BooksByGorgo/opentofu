# A Web Server on Your Machine

**The need.**
A configuration that only runs `echo` is talking to itself.
Real things live behind APIs: a container runtime, a source hosting service, a cloud.
The tool cannot know every API, so it needs a way to load the vocabulary for each one, to pin which version of that vocabulary everyone uses, and to authenticate without credentials in the files.
Once there are several resources, they depend on each other, values have to be computed from other values, and something has to test that the result actually works.

**Why it matters.**
Providers are how one language reaches every cloud and service, and version pinning is what makes a configuration produce the same result on a colleague's machine next year.
Dependencies derived from references are what replace the carefully ordered steps of a script.
A check that runs after every apply is the difference between "it applied" and "it works".

**Why it is hard.**
Every provider has its own authentication and its own release cadence, and a new major version can rename arguments.
The order of operations is nowhere written down; it has to be inferred from what refers to what.
A change in an input, like an edited source file, has to turn into a rebuild without anyone tracking it by hand.

**The strategy.**
Load providers through `required_providers` with constrained versions and a lock file, keep credentials in the environment, and let references between resources build the dependency graph.
Compute derived values with locals and functions, and finish with a `check` block that tests the result.
The example that exercises all of it is a small Go web server: the Docker provider builds its image and runs the container, the GitHub provider creates the repository for its source, and the HTTP provider verifies that it answers.

## The program

\index{Go}
The web server is as small as a web server gets.
Create the directory `webserver` for this chapter's configuration, and put the program in `webserver/app/main.go`:

```go
package main

import (
	"fmt"
	"log"
	"net/http"
	"os"
)

func hello(w http.ResponseWriter, r *http.Request) {
	fmt.Fprintln(w, "Hello, World!")
}

func main() {
	addr := ":8080"
	if port := os.Getenv("PORT"); port != "" {
		addr = ":" + port
	}
	http.HandleFunc("/", hello)
	log.Printf("listening on %s", addr)
	log.Fatal(http.ListenAndServe(addr, nil))
}
```

It needs a module file, `app/go.mod`:

```
module motd

go 1.26
```

Check it works before involving any other tool:

```session
$ cd webserver/app
$ go run . &
$ curl localhost:8080/
Hello, World!
```

\index{Dockerfile}
The container image is described by `app/Dockerfile`, in two stages: one with the Go toolchain to build a static binary, and one that ships nothing but the binary:

```dockerfile
# stage 1: build a static binary
FROM golang:1.26 AS build
WORKDIR /src
COPY go.mod ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /motd .

# stage 2: ship only the binary
FROM scratch
COPY --from=build /motd /motd
EXPOSE 8080
ENTRYPOINT ["/motd"]
```

The result is an eight megabyte image with one file in it.
Also add `app/.dockerignore` containing `.git`, so that the repository history does not get copied into the build.

Do not run `docker build` yourself.
Writing the Dockerfile is the whole of your job here; building the image from it is a resource in the configuration, and `tofu apply` will build it, and rebuild it whenever the source changes.

## Providers

\index{provider}
\index{required\_providers}
The configuration files are in the `webserver` directory, which is the parent directory of `app`.
This chapter splits configuration across several files, which is the normal way to organize a configuration, starting with `versions.tf`:

```terraform
terraform {
  required_version = ">= 1.6"

  required_providers {
    docker = {
      source  = "kreuzwerker/docker"
      version = "~> 3.0"
    }
    github = {
      source  = "integrations/github"
      version = "~> 6.0"
    }
    http = {
      source  = "hashicorp/http"
      version = "~> 3.4"
    }
  }
}
```

\index{provider!source}
`required_providers` lists every provider the configuration uses.
Each entry has a **source**, which is an address in the provider registry written as `namespace/name`, and a **version** constraint.
The local name on the left (`docker`) is what the rest of the configuration uses, and by convention it matches the name in the source.

\index{version constraint}
\index{\textasciitilde>}
The `~>` operator is the **pessimistic constraint**: `~> 3.0` means "3.0 or newer, but still 3", so any 3.x release is acceptable and 4.0 is not.
Providers follow semantic versioning, so a major version bump can rename arguments and break your configuration.
Pinning the major version lets you take bug fixes automatically and take breaking changes on purpose.

\index{provider block}
Each provider can also have a `provider` block that configures it, in `providers.tf`:

```terraform
provider "docker" {
  # talks to the local docker daemon; set host for a remote one, e.g.
  # host = "ssh://ubuntu@my-server"
}

provider "github" {
  # reads the token from the GITHUB_TOKEN environment variable
}
```

Both blocks are empty because the defaults are correct: the Docker provider talks to the local daemon socket, and the GitHub provider reads a token from the environment.
An empty `provider` block is optional, but writing one is a good place to document where the credentials come from.

::: {.tip}
**Trap:** Never put a token in a `provider` block, a variable default, or a `.tfvars` file that is committed.
Providers read credentials from environment variables or from the same configuration files the vendor's own command line tools use, and that is where credentials should stay.
For GitHub, `export GITHUB_TOKEN=$(gh auth token)` borrows the token the `gh` tool already has.
:::

\index{tofu init}
\index{.terraform}
\index{lock file}
\index{.terraform.lock.hcl}
Run `init` and the providers are downloaded:

```session
$ tofu init
- Installing integrations/github v6.13.0...
- Installing hashicorp/http v3.6.1...
- Installing kreuzwerker/docker v3.9.0...
```

Two new things appear in `webserver`.
`.terraform/` holds the downloaded plugins; it is a cache and belongs in `.gitignore`.
`.terraform.lock.hcl` is the **dependency lock file**: it records the exact provider versions that were selected and their checksums, so that everyone who runs `init` on this configuration gets the same providers.
In a real project you commit the lock file; Appendix A has the details, including what to do for colleagues on other platforms.

## Files and the graph

\index{module!root}
Every `.tf` file in `webserver` is part of the same configuration.
The tool takes the union of all of them, as if they were one file, and then works out the order of operations from the **references** between blocks, not from the order of files or lines.
You could put every block in a single `main.tf` and nothing would change; splitting the configuration into `versions.tf`, `providers.tf`, `variables.tf`, and `main.tf` is only for the humans.

::: {.tip}
**Wut:** There is no "top" of a configuration.
You can refer to a resource defined in another file, or later in the same file, and the tool builds a dependency graph from every reference.
If A mentions B, then B is created before A and destroyed after it.
That single rule replaces most of the ordering you would write by hand in a script.
:::

`variables.tf` declares the one input:

```terraform
variable "port" {
  type        = number
  description = "Host port the web server is published on."
  default     = 8080

  validation {
    condition     = var.port > 1024 && var.port < 65536
    error_message = "port must be an unprivileged port (1025-65535)."
  }
}
```

## Building the image

\index{docker\_image}
\index{locals}
`main.tf` begins with the image:

```terraform
locals {
  app_dir = "${path.module}/app"
  # changes whenever any file under app/ changes
  app_hash = sha1(join("", [for f in fileset(local.app_dir, "**") :
    filesha1("${local.app_dir}/${f}")
  ]))
}

resource "docker_image" "web" {
  name = "motd:ch2"

  build {
    context = local.app_dir
  }

  triggers = {
    src = local.app_hash
  }
}
```

\index{local value}
\index{local.}
A `locals` block defines **local values**: named expressions.
Where a variable is set by the user, a local is computed by the configuration.
Use one whenever you would otherwise write the same expression twice, or when an expression deserves a name.
They are referenced as `local.NAME` (singular, which trips people up).

\index{path.module}
`path.module` is the directory containing the configuration, so `"${path.module}/app"` is the `app` directory no matter where you run `tofu` from.

\index{for expression}
\index{fileset}
\index{filesha1}
`app_hash` is the first expression with real machinery in it, so read it from the inside out.
`fileset(dir, "**")` returns the set of every file under a directory.
`[for f in ... : filesha1(...)]` is a **for expression**: it produces a new list by evaluating the expression after the colon once for each element.
If you know list comprehensions from Python, it is the same idea with the parts in a different order.
`join("", ...)` concatenates the hashes and `sha1` boils them down to one string that changes whenever any file in `app/` changes.

`docker_image` is a resource type defined by the Docker provider, and the prefix before the first underscore is how you can tell: the type name starts with the provider's name, and that is also how the tool knows which plugin to hand the block to.
The provider defines a family of such types, `docker_container`, `docker_network`, and `docker_volume` among them, each with its own arguments and attributes, and its documentation lists all of them [@DockerProviderDocs].

The `build` block tells the Docker provider to build the image from that directory instead of pulling it.
`triggers` is a map of values that force a rebuild when they change, and the source hash is the natural thing to put there.
Without it, editing `main.go` would not rebuild anything, because the provider has no way to know the source changed.

## Running the container

\index{docker\_container}
\index{reference}
Add the container to `main.tf`, after the image:

```terraform
resource "docker_container" "web" {
  name  = "motd"
  image = docker_image.web.image_id

  ports {
    internal = 8080
    external = var.port
  }
}
```

\index{attribute}
`image = docker_image.web.image_id` is a **reference** to another resource's attribute.
It does two things at once: it supplies the value, and it tells the tool that the container depends on the image, so the image is built first.
Attributes like `image_id` are only known after the image exists, which is why plans show them as `(known after apply)`.

`ports` is a **nested block**, a block inside a resource that groups related arguments.
A resource type can allow several of the same nested block, and a container with two published ports has two `ports` blocks.

The two arguments are two sides of one door.
`internal` is the port inside the container, the one the program listens on; `external` is the port on your machine that Docker connects to it.
The web server always listens on 8080, so `internal` is fixed, but nothing outside the container has to know that: the container can publish it as any port you like, which is why `external` comes from a variable and `internal` does not.
Set `port` to 9000 and `http://localhost:9000/` reaches a server that still thinks it is on 8080.

## The repository

\index{github\_repository}
You could put the GitHub configuration in `main.tf`, but a separate file called `github.tf` keeps it apart from the container.
This defines the repository the code will live in:

```terraform
resource "github_repository" "motd" {
  name        = "tasting-tofu-motd"
  description = "message of the day web server"
  visibility  = "private"
}

output "clone_url" {
  value = github_repository.motd.ssh_clone_url
}
```

Three arguments, and the provider fills in the rest with defaults; a plan lists all of them.
The output hands back the clone URL so that you can push the code.

## Checking the result

\index{check}
\index{assert}
\index{data source}
The last block in `main.tf` is a test:

```terraform
check "hello" {
  data "http" "web" {
    url = "http://localhost:${docker_container.web.ports[0].external}/"

    retry {
      attempts     = 5
      min_delay_ms = 1000
    }
  }

  assert {
    condition     = trimspace(data.http.web.response_body) == "Hello, World!"
    error_message = "the web server did not say hello"
  }
}
```

A `check` block is a unit test for infrastructure.
It runs on every plan and apply, after everything else, and reports whether an assertion holds.

\index{data block}
Inside it is a `data` block, the first one in the booklet.
A **data source** is a read-only lookup: where a resource creates something, a data source fetches something that already exists.
`data "http"` fetches a URL and exposes the `status_code` and `response_body`.
Data sources are referenced with a `data.` prefix, so the body is `data.http.web.response_body`.

The URL references the container's published port, and that reference is what makes the check wait for the container to exist.
`retry` keeps trying for a few seconds because a container answers a moment after it starts.
The `assert` block then compares the body with what you expect.

::: {.tip}
**Wut:** A failed `check` is a warning, not an error.
Apply completes, the resources are all there, and the output says `Warning: Check block assertion failed`.
That is deliberate: a check tests the result without holding the deployment hostage.
When you want a failure to stop the apply, use a `postcondition` instead, which Chapter 3 introduces.
:::

Finally, add an output to `main.tf` that tells you where to look:

```terraform
output "url" {
  value = "http://localhost:${var.port}/"
}
```

## Running it

Export the GitHub token, then initialize and plan from `webserver`:

```session
$ export GITHUB_TOKEN=$(gh auth token)
$ tofu init
...
$ tofu plan
  # github_repository.motd will be created
  + resource "github_repository" "motd" {
      + allow_merge_commit     = true
      + default_branch         = (known after apply)
      + description            = "message of the day web server"
      + name                   = "tasting-tofu-motd"
      + ssh_clone_url          = (known after apply)
      + visibility             = "private"
      ...
    }

Plan: 3 to add, 0 to change, 0 to destroy.

Warning: Check block assertion known after apply
```

The warning is the check saying it cannot run yet because the container does not exist.
Apply, and it runs at the end:

```session
$ tofu apply
docker_image.web: Creating...
docker_image.web: Creation complete after 16s [id=sha256:513b4a...motd:ch2]
docker_container.web: Creating...
docker_container.web: Creation complete after 1s [id=0d901a5012b5...]
github_repository.motd: Creating...
github_repository.motd: Creation complete after 3s [id=tasting-tofu-motd]

Apply complete! Resources: 3 added, 0 changed, 0 destroyed.

Outputs:

clone_url = "git@github.com:you/tasting-tofu-motd.git"
url = "http://localhost:8080/"
```

```session
$ curl localhost:8080/
Hello, World!
```

Now push the code to the repository the tool just created:

```session
$ cd app
$ git init && git add . && git commit -m "hello world web server"
$ git remote add origin $(tofu -chdir=.. output -raw clone_url)
$ git push -u origin main
```

\index{-chdir}
`-chdir` runs the command as if you were in the configuration directory, which saves a `cd` in scripts.

Before changing any code, change the port from the command line and watch it move:

```session
$ cd ..
$ tofu apply -auto-approve -var "port=8888"
  # docker_container.web must be replaced
-/+ resource "docker_container" "web" {
      ~ ports {
          ~ external = 8080 -> 8888 # forces replacement
            # (3 unchanged attributes hidden)
        }
    }

Plan: 1 to add, 0 to change, 1 to destroy.

Changes to Outputs:
  ~ url = "http://localhost:8080/" -> "http://localhost:8888/"
docker_container.web: Destroying... [id=38f5e4968839...]
docker_container.web: Destruction complete after 0s
docker_container.web: Creating...
docker_container.web: Creation complete after 1s [id=4f97b176314b...]

Apply complete! Resources: 1 added, 0 changed, 1 destroyed.

Outputs:

url = "http://localhost:8888/"
$ curl localhost:8888/
Hello, World!
```

\index{-auto-approve}
A published port cannot be changed on a running container, so the provider marks it `# forces replacement` and the container is destroyed and created again; the image is untouched, because nothing about it changed.
The `url` output follows the variable, and port 8080 no longer answers.
`-auto-approve` skips the confirmation prompt, which is fine on your own laptop while you experiment and a bad habit anywhere else (Appendix A).

## Changing the code

Edit `main.go` so that it says something else and run `tofu plan`:

```session
$ tofu plan
  # docker_container.web must be replaced
-/+ resource "docker_container" "web" {
      ~ image = "sha256:513b4a..." -> (known after apply) # forces replacement
      ...
    }

  # docker_image.web must be replaced
-/+ resource "docker_image" "web" {
      ~ triggers = { # forces replacement
          ~ "src" = "97bf81ab..." -> "b860b2aa..."
        }
    }

Plan: 2 to add, 0 to change, 2 to destroy.
```

The source hash changed, so the image is replaced; the image id will change, so the container is replaced.
Nothing about the repository changed, so it is left alone.
Apply, and the new server is running.
That plan is the whole point of the chapter: the tool worked out the two things that need to happen from one edit to a Go file.

::: {.tip}
**Tip:** If the container fails to start with `Bind for 0.0.0.0:8080 failed: port is already allocated`, something else on your machine owns the port.
Apply again with `-var port=8081`.
The variable is there so that you do not have to edit the configuration to work around your laptop.
:::

## Shutting it down

\index{tofu destroy}
When you are done, `destroy` takes down everything the configuration created, in the reverse of the order it was created:

```session
$ tofu destroy
  # docker_container.web will be destroyed
  # docker_image.web will be destroyed
  # github_repository.motd will be destroyed

Plan: 0 to add, 0 to change, 3 to destroy.

Do you really want to destroy all resources?
  Enter a value: yes

docker_container.web: Destroying... [id=61b2a04defb3...]
docker_container.web: Destruction complete after 1s
docker_image.web: Destroying... [id=sha256:513b4a...motd:ch2]
docker_image.web: Destruction complete after 0s
github_repository.motd: Destroying... [id=tasting-tofu-motd]
github_repository.motd: Destruction complete after 1s

Destroy complete! Resources: 3 destroyed.
```

The container goes first because it depends on the image, then the image, then the repository.
Afterwards `docker ps -a` and `docker image ls` show no trace of `motd`, and the state file records no resources.
The source in `app` is untouched, and so is the git history in your working copy; only the copy on GitHub is gone.

::: {.tip}
**Trap:** `tofu destroy` destroys everything in the state, including the GitHub repository and its history.
For things you want to keep, add `lifecycle { prevent_destroy = true }` to the resource, which makes any plan that would destroy it fail.
Alternatively, `tofu state rm github_repository.motd` makes the tool forget the repository without deleting it, and a later `tofu apply` would then try to create it again.
:::

Deleting a repository needs the `delete_repo` scope on the token, which `gh auth token` does not grant by default; without it the destroy stops at the repository with a permission error, and `gh auth refresh -s delete_repo` adds the scope.

## Key Points

- A provider is a plugin that adds resource types by translating them into API calls.
  `required_providers` says which ones you need; `init` downloads them; the lock file pins them.
- Credentials come from the environment or the vendor's own config files, never from your files.
- All `.tf` files in a directory are one configuration, and references between blocks determine the order of operations.
- Locals name computed values; variables hold user-supplied ones.
- A reference to another resource's attribute both supplies a value and creates a dependency.
- Data sources read things that exist; resources create things.
- `check` blocks test the result of an apply and warn when it is wrong.
- Content hashes turn "the source changed" into "the image must be rebuilt" without anyone tracking it by hand.

## New Syntax

| Syntax | What it is |
|:------------------------|:-------------------|
| `required_providers { NAME = { source, version } }` | Which plugins the configuration needs |
| `version = "~> 3.0"` | Pessimistic constraint: any 3.x |
| `provider "NAME" { }` | Configuration for a provider |
| `locals { NAME = expr }` | Named expressions, referenced as `local.NAME` |
| `path.module` | Directory containing the configuration |
| `[for x in list : expr]` | For expression: build a list from a list |
| `fileset`, `filesha1`, `join`, `sha1` | File and hash functions |
| `TYPE.NAME.ATTR` | Reference to a resource attribute (and a dependency) |
| `ports { ... }` | A nested block inside a resource |
| `data "TYPE" "NAME" { }` | A read-only lookup, referenced as `data.TYPE.NAME` |
| `check "NAME" { data ...; assert { condition, error_message } }` | A test that runs after every plan and apply |
| `list[0]` | Indexing into a list |
| `tofu -chdir=DIR ...` | Run as if in another directory |

## Try It

- Change the container to restart automatically with `restart = "unless-stopped"`, reboot Docker, and confirm the server comes back.
- Add a `github_repository_file` resource that manages `README.md` in the repository, and see what happens to the plan when you edit the README on GitHub.
- Add `lifecycle { prevent_destroy = true }` to the repository and run `tofu plan -destroy`.
- Make the check fail on purpose by changing the expected string, and watch apply complete anyway.
  Then look at `tofu show` and find the check result in the state.
- Put the `check` block in its own file, `checks.tf`, and confirm nothing changes.
  Files are just organization.
- Write a GitHub Actions workflow in the repository that runs `tofu fmt -check` and `tofu validate` on every push.
  Both need no credentials.
